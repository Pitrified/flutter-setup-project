# Structured Streaming - AS-IS + Injection Points

Companion to `00.1_initial_research.md` (generic AG-UI/Flutter primer). This
file is repo-specific: how `fala` connects to the LLM today, and exactly where
a *structured* streaming layer would be injected so the rich tutor widget
(correction card + conversation bubble + per-error rows) renders in real time,
not just a flat token stream.

Goal restated: stream the **typed `TutorResponse`** as it is generated, so the
`CorrectionCard` and translation-aware `MessageBubble` fill in field-by-field
(corrected sentence, then each error row, then the conversational reply), rather
than blocking on the full JSON and snapping the whole widget in at once.

---

## 1. AS-IS: how we connect to the LLM today

The pipeline is **request/response, fully buffered**. Nothing streams to the UI;
the conversation bubble appears only after the entire JSON response is parsed.

### 1.2 The two real engines

**OpenAI (`openai_inference_engine.dart`)** - the network path:
- `client.chat.completions.create(...)` - a **single non-streaming call**
  (`openai_inference_engine.dart:92`).
- Output is constrained with OpenAI strict structured outputs:
  `responseFormat: ResponseFormat.jsonSchema(name, schema)` where `schema` is
  `tutorResponseJsonSchema` (`tutor_response_schema.dart`) - mirrors the freezed
  model exactly, `additionalProperties:false`, all fields required. So the raw
  text is guaranteed well-formed JSON of the right shape.
- Reads API key + model id on every `generate`; rebuilds `OpenAIClient` only
  when the key changes.
- **Endpoint freedom:** we own this code, so we are not locked to Chat
  Completions. The newer **Responses API** (`/v1/responses`) streams
  semantic/typed events (`response.output_text.delta`,
  `response.refusal.delta`, plus structured-output deltas) rather than raw
  `choice.delta.content`, which is a better fit for structured streaming. If
  `openai_dart` exposes it (or we hit the endpoint directly), the
  `generateStream` contract below is unchanged - the engine just adapts a
  richer upstream event into our internal raw-text/field stream. Treat the
  engine as the *only* place that knows which OpenAI endpoint we use.

**flutter_gemma (`flutter_gemma_engine.dart`)** - the on-device path:
- Already token-streams internally:
  `await for (final response in chat.generateChatResponseAsync())` collecting
  `response.token` into a `StringBuffer` (`flutter_gemma_engine.dart:68`).
- **Crucially, the stream is consumed and thrown away** - we await the whole
  loop, then return one `InferenceSuccess(rawText: buffer.toString())`. The
  token-level granularity that streaming UI needs is discarded right here.
- No constrained decoding wired up yet (schema enforcement is OpenAI-only).

### 1.3 Why nothing streams to the UI

Three hard buffering boundaries, each a place where a partial result is
collapsed to a final value:

1. **`InferenceEngine.generate` returns `Future<InferenceResult>`** - a single
   value, not a `Stream`. The interface has no streaming method at all
   (`inference_engine.dart:57`). Even gemma's internal stream dies here.
2. **`StructuredInferenceEngine.generate` is `async` and parses once** - it can
   only run the parser after the full `rawText` exists
   (`structured_inference_engine.dart:80`); `StructuredOutputParser` is a pure
   `String -> ParseResult<T>`, all-or-nothing on a complete JSON document.
3. **`ConversationController.sendMessage` is one `await`** then a single
   `appendMessage` - the tutor message materializes fully-formed; the UI's only
   "in progress" signal is the boolean `_isSending` driving a `TypingIndicator`
   (`conversation_screen.dart:135`).

There is **already a reactive UI spine** we can reuse: `conversationStream`
(broadcast `StreamController<Conversation?>`) -> `StreamBuilder` in the screen.
The streaming work is about feeding *partial* states into that spine (or a
sibling stream) rather than a single terminal state.

## 2. The structured-streaming problem (specific to us)

A naive token stream gives `state.textBuffer += delta` and a single growing
`Text` widget (that is the `00.1` blueprint). We want more: the model is
emitting a JSON document, and we want to **lift partial JSON into a partial
typed object** so each sub-widget reacts to *its own* field.

Target render order as bytes arrive (matches our schema field order):

```
correction.content      -> corrected sentence line (top of CorrectionCard)
correction.translation  -> dim translation under it
correction.errors[i]    -> one strike/replace row per element, appearing as completed
conversation.content    -> the chat bubble text (MessageBubble), token by token
conversation.translation-> tap-to-reveal line (can arrive last, no UI urgency)
```

The core difficulty: **`TutorResponse.fromJson` requires every field** (freezed,
all `required`). You cannot call it on half a document. So mid-stream you do not
have a `TutorResponse` - you have a partial. We model the partial *generically*
(one delta type for any schema, no per-`T` boilerplate) and only materialize the
typed `T` at completion - see section 4 for how, including streaming nested
objects (each correction) live *as they arrive*.

## 3. Where to inject - three concrete options

Ordered cheapest-to-richest. All reuse the existing `conversationStream` spine.

### Option S1: Token stream only (text typing effect, no structure)

Add a streaming method to the engine that yields raw token deltas; surface
`conversation.content` characters as they arrive into the bubble; parse the full
typed `TutorResponse` once at the end (correction card still snaps in at the
end). This is the `00.1` blueprint applied to our chat bubble.

- **Inject at:** new `Stream<String> generateStream(request)` on `InferenceEngine`;
  controller exposes a `Stream<String>` for the in-flight tutor message; screen
  renders it in a dedicated widget while `_isSending`.
- **Pro:** small, gemma already produces the tokens; OpenAI just swaps
  `create` -> `createStream`.
- **Con:** does NOT meet the brief - the rich correction widget is still
  all-or-nothing. Good as a stepping stone, not the destination.

### Option S2: Streaming structured deltas (RECOMMENDED) - partial typed object

Keep the JSON-document approach but parse it **incrementally**. As bytes arrive,
run a *lenient/partial* JSON parse and project the partial map onto a
`PartialTutorResponse`. Emit that partial on every meaningful change; each
sub-widget reads the field it cares about and renders when present.

- **Inject at THREE places:**
  1. **Engine** - add a streaming generate that yields the *cumulative* raw text
     (`Stream<String>` of the buffer-so-far, or token deltas the caller
     accumulates). For OpenAI use `createStream()` + `delta.content`; for gemma,
     stop discarding the loop and yield the running buffer.
  2. **A streaming structured layer** - new `StructuredStreamEngine<T>` (sibling
     to `StructuredInferenceEngine<T>`) that maps the raw-text stream through a
     **partial parser** and yields `Stream<StructuredDelta<T>>` (a partial value
     + an `isComplete` flag + terminal failure modes).
  3. **Controller/UI** - `ConversationController` exposes the partial stream for
     the in-flight tutor turn; the screen renders a live `MessageBubble` +
     `CorrectionCard` bound to the partial, then on completion appends the final
     `TutorResponse` message exactly as today (persistence unchanged).
- **Pro:** meets the brief; reuses freezed model, schema, widgets; final-state
  path (persist + parse) stays identical, so it is additive, not a rewrite.
- **Con:** need a partial/lenient JSON parser (section 4) and a partial model.

### Option S3: Full AG-UI event protocol

Adopt AG-UI events end-to-end (`TEXT_MESSAGE_CONTENT`, `STATE_DELTA` as RFC-6902
JSON Patch, `TOOL_CALL_*`, lifecycle). **AG-UI's value is its ecosystem, and
that ecosystem is Python/JS** (CopilotKit, LangGraph, ready-made front ends). In
Flutter there is no such ecosystem to plug into, so AG-UI would be a wire format
we both produce and consume ourselves - i.e. ceremony without the payoff. It is
**not a requirement**; adopt it only if we add a server-side agent backend that
already speaks it. Otherwise it is noise, not help, and we skip it.

We still borrow one cheap idea from it (see section 5): naming S2's internal
field-change events after AG-UI keys, so *if* a server agent ever appears the
migration is mechanical. That is a naming convention, not a dependency.

## 4. Partial parsing strategy (the heart of S2)

`TutorResponse.fromJson` cannot run on incomplete JSON. Options:

The cumulative buffer is parsed each tick by a tolerant parser that closes open
strings / braces / arrays and returns a best-effort `Map<String, dynamic>`. The
open design question is what that map is *projected onto* - and this is where
the genericity requirements (section 2 of the request) bite. Three layers,
cheapest to richest:

#### 4a. The partial parser stays fully generic (no per-schema code)
The tolerant `String -> Map<String,dynamic>?` parser knows nothing about
`TutorResponse`. Reuse it for every schema. Either:
- **`llm_json_stream`** (pub.dev) - reactive streaming JSON parser for LLM
  output, path-based subscriptions (`correction.content`,
  `correction.errors[0].corrected`), values chunk-by-chunk. Schema-agnostic by
  construction; maps cleanly onto field-per-widget.
- or a ~120-line vendored tolerant scanner (zero deps; fine because the parser
  is generic even if our schemas are few).

This layer is already "write once, any schema." The repetition risk
(requirement 2.1) lives entirely in the *typed* layer above it.

#### 4b. Avoiding one hand-written `PartialT` per `T` (requirement 2.1)
Hand-rolling a `PartialTutorResponse` per response type is acceptable but
repetitive. Options to skip the repetition, in increasing cleverness (we prefer
the *least* clever that works):

- **Option G1 - generic delta carries the raw partial map (recommended baseline).**
  Do not mint a `PartialT` at all for transport. The stream yields:

  ```dart
  class StructuredDelta<T> {
    final Map<String, dynamic> partial; // best-effort map, any depth
    final T? value;                     // non-null only when isComplete
    final bool isComplete;
    final StructuredFailure? failure;   // terminal inference/parse failure
  }
  ```

  Widgets read fields by path from `partial` (`partial['correction']?['content']`
  or via a tiny typed accessor extension). One generic type, zero per-schema
  classes. Con: field access is stringly-typed at the leaf - acceptable for the
  handful of fields a streaming widget actually watches, and the *final* `value`
  is still fully typed via the existing `fromJson`.

- **Option G2 - codegen the `PartialT` from the freezed model.** A small
  build_runner generator emits `PartialTutorResponse` (all-nullable mirror +
  `fromPartialJson(Map)` + `isComplete`) next to each `@freezed` model tagged
  with an annotation. Gives compile-time-typed partial access with no hand
  repetition. Con: a generator to own; only worth it if many schemas stream or
  if stringly-typed leaves in G1 prove error-prone. Defer until G1 hurts.

- **Option G3 - `fromJson` tolerant of nulls.** Make models accept partials
  directly (nullable fields / defaulted). Rejected: pollutes the domain model,
  loses the "complete means valid" guarantee, and fights freezed. Mentioned only
  to dismiss.

**Recommendation: ship G1, keep G2 in pocket.** G1 satisfies "generic for any
schema" with no repetition and no weird complexity elsewhere; the typed `value`
on completion is unchanged.

#### 4c. Streaming nested objects *as they arrive* (requirement 2.2, flipped)
Preferred behavior: do **not** wait for an element to complete. Emit each nested
object / array element the moment it appears and let its own leaves fill in
live - so `correction.errors[2]` shows its `original` while `corrected` and
`explanation` are still streaming, and a row's text grows token-by-token. Same
"typing" effect we want for the bubble, now applied at every depth.

Generic rule, schema-independent:

> Expose whatever the tolerant parser currently holds, at every depth, with all
> leaves nullable/partial. An array of length-so-far `k` exposes `k` elements
> (the last one partial); a nested object exposes the leaves seen so far; a
> mid-token string is exposed as its current prefix.

**How much more complexity? Small at the data layer, moderate at the widgets.**

*Data/parser layer - basically free, arguably simpler:*
- The tolerant parser (4a) **already produces** these partial subtrees; the old
  "complete only" rule was a *filter on top* (the round-trip-completeness check).
  Flipping the rule **removes** that gate - less code, not more.
- This pairs naturally with **G1** (map transport): the partial map is already
  recursively nullable, so `partial['correction']?['errors']?[2]?['corrected']`
  works with zero extra plumbing. No change to the delta type.
- `llm_json_stream` exposes per-path values chunk-by-chunk, which is exactly the
  arrive-as-you-go shape.
- One signal you still need: an **array-closed flag** (and per-element-closed),
  so the UI knows when to stop expecting a new `errors[k]` and to mark a row
  final. Cheap: it is just "did this `]`/`}` arrive yet."

*Widget layer - where the real cost is (moderate, per-widget polish):*
- Rows/leaves must tolerate `null` and mid-token strings: render a skeleton or
  placeholder for a not-yet-arrived `corrected`, and accept that the last token
  may flicker (`corrigid` -> `corrigido` -> `corrigidos`). For the strike/replace
  `CorrectionCard` row this needs a deliberate partial state, not just the final
  layout.
- Layout stability: stable `key`s per element index, and `AnimatedSize`/reflow
  tolerance so growing text does not jump. Coalesce/debounce emissions (already
  recommended for anti-jank) to keep flicker and rebuild cost down.

*If we choose G2 (codegen) instead of G1:* the generated `PartialT` must be
**recursively** partial (`PartialCorrectionError` with nullable leaves too), not
just top-level nullable - meaningfully more generator work. This is the main
reason the flip nudges us further toward **G1**, where recursion is free.

**Verdict:** flipping to arrive-as-you-go costs ~nothing in the parser/transport
(it removes a gate and rides G1's nullable map) and a bounded amount of
*widget-side* polish (placeholders + anti-flicker + element keys) plus a tiny
array-closed flag. It stays fully generic over depth - the rule keys off JSON
structure, never off `TutorResponse`. The old completeness-gated behavior is
still worth keeping as a per-widget opt-in for any field where a half-rendered
value would be misleading rather than just "typing."

### 4b. Token-boundary heuristic on the typed sub-strings
Because our schema is fixed and flat, we could stream only the two
human-visible long strings (`correction.content`, `conversation.content`) by
locating their JSON keys in the buffer and emitting the in-progress string
value, while treating `errors[]` as atomic (render only when the array closes).
Lighter than a general parser, but brittle to escaping/whitespace - prefer 4a.

### 4c. (OpenAI-specific) it is still one JSON document
OpenAI strict structured output streams the *same* JSON, token by token via
`delta.content`. There is no separate "structured stream"; you accumulate
`delta.content` into a buffer and apply 4a to the buffer each tick. So the
partial parser is shared across both engines - good, one code path.

**Anti-jank note (from `00.1`):** at ~15 ms/token, do not rebuild the whole
ListView per token. Bind each sub-widget to a granular `ValueListenable` /
`select`ed provider slice keyed to its field, and debounce/coalesce emissions
(e.g. emit on field-change or every N ms), so only the changed line repaints.

## 5. AG-UI patterns - verified (reference only, not adopted)

Kept as reference so we can name S2 internals compatibly and recognize the
pattern if a server agent shows up - **not** because we are taking on AG-UI in
the Flutter app (see S3: the ecosystem that makes it worthwhile is Python/JS).
Confirmed the `00.1` references against current sources. The protocol defines
**16-17 event types** in five groups. Relevant ones:

- **Lifecycle:** `RUN_STARTED`, `RUN_FINISHED`, `RUN_ERROR`, `STEP_STARTED`,
  `STEP_FINISHED`. (`00.1` used `RUN_STARTED/FINISHED` - correct.)
- **Text message (the "typing" trio):** `TEXT_MESSAGE_START` (`messageId`,
  `role`), `TEXT_MESSAGE_CONTENT` (carries a **`delta`** text chunk - note:
  `delta`, not `payload.content` as the `00.1` blueprint wrote), `TEXT_MESSAGE_END`.
- **Tool call:** `TOOL_CALL_START` (`toolCallId`, `toolName`), `TOOL_CALL_ARGS`
  (streamed arg `delta`), `TOOL_CALL_END`, `TOOL_CALL_RESULT`.
- **State:** `STATE_SNAPSHOT` (full state), `STATE_DELTA` (**JSON Patch /
  RFC 6902** ops, e.g. `[{"op":"replace","path":"/user/status","value":"active"}]`),
  `MESSAGES_SNAPSHOT` (full history resync).
- **Special:** `RAW`, `CUSTOM` (`name` + `value`).

Mapping to our case if we ever go S3: the tutor turn is one `TEXT_MESSAGE_*`
sequence for `conversation.content`, and the correction block is naturally a
`STATE_DELTA` stream of JSON-Patch ops into a shared `tutorResponse` state
object - which is conceptually identical to S2's partial-projection, just with a
standardized wire format. So **S2 is a subset of S3**; building S2 with
field-change events named after AG-UI keeps the door open without the protocol
overhead now.

Correction to carry back to `00.1`: its blueprint reads
`payload['content']` / `event['payload']`; the real AG-UI shape is a flat event
with `type` + `delta` (text) or `delta` (JSON-Patch array for state). Minor, but
worth fixing if that code is ever used as a literal starting point.

## 6. Recommendation

1. **Build S2.** It is the smallest change that satisfies "render the rich
   widget in real time." It is additive: the existing one-shot
   `StructuredInferenceEngine` + persistence path stay for the *final* message;
   the streaming layer is a parallel `Stream<StructuredDelta<TutorResponse>>`
   for the in-flight turn only.
2. **Keep it generic for any schema (G1).** The streaming layer is typed
   `StructuredStreamEngine<T>` but transports a best-effort
   `Map<String,dynamic> partial` plus a typed `T? value` (non-null only at
   completion). No hand-written `PartialT` per schema, no `fromJson` changes.
   Promote to codegen (G2) only if stringly-typed leaf access starts hurting.
   See section 4b.
3. **Three injection points, in order:**
   - `InferenceEngine`: add `Stream<String> generateStream(InferenceRequest)`
     (OpenAI: `createStream` accumulating `delta.content`, or the Responses API
     deltas if we move to it - the engine hides which endpoint; gemma: yield the
     running buffer instead of discarding it; fake: chunk a fixture).
   - New `StructuredStreamEngine<T>`: raw-text stream -> generic tolerant parse
     -> `Stream<StructuredDelta<T>>` (`partial` map, `value`, `isComplete`,
     `failure`). Nested objects/array elements stream in *as they arrive*
     (section 4c, flipped), so each correction row appears immediately and its
     leaves fill in live; a per-widget completeness gate stays available where a
     half-rendered value would mislead.
   - `ConversationController` + `ConversationScreen`: expose/consume the partial
     stream; bind `MessageBubble` and `CorrectionCard` to granular slices to
     avoid per-token full-list rebuilds; on `isComplete`, append the final typed
     message exactly as today.
4. **Partial parser:** start with `llm_json_stream` (path subscriptions match
   our field-per-widget + per-element need); fall back to a ~120-line vendored
   tolerant scanner if we want zero deps (section 4a). Both stay schema-agnostic.
5. **Skip AG-UI in Flutter.** Its payoff is the Python/JS ecosystem we cannot
   use here; adopting the wire format on both ends would be noise. Only name S2's
   internal events after AG-UI keys (free future-proofing) and revisit the full
   protocol if a server-side agent that speaks it ever appears.
