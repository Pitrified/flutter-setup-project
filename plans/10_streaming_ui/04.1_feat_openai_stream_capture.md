# Phase 4.1 - Capture a golden OpenAI SSE fixture (deferred / optional)

## Status

**Deferred.** Decision 2026-06-22: trust the contract (openai_dart's generated
parser + the OpenAI OpenAPI spec) for now; revisit this phase only if we observe
streaming bugs in practice. This file records the analysis and the concrete plan
so it is ready to pick up, not throwaway.

## Why this exists

Phase 4's OpenAI streaming test hand-authors an SSE body, feeds it through the
SDK's real `SseParser` + `ChatStreamEvent.fromJson`, and asserts the adapter
accumulates correctly. That proves **"given well-formed `ChatStreamEvent`s, the
adapter does the right thing."** It does not prove two things:

1. that OpenAI's real bytes for *our exact request* (strict `json_schema` mode +
   our model) match the shape we hand-authored, and
2. the behavioral assumption the adapter comment leans on: that the
   concatenation of streamed `delta.content` equals the final valid JSON with
   nothing extra - i.e. **every cumulative buffer is a true prefix of one valid
   document** (no role-only first chunk carrying junk, no trailing `usage` chunk
   polluting the text buffer, content never null mid-stream in a reordering way).

## Two distinct risks (and what buys each down)

- **Format / per-event JSON shape** (`chat.completion.chunk`,
  `choices[].delta.content`): covered by the OpenAI OpenAPI spec (the
  `openai-openapi` repo) and openai_dart's generated `ChatStreamEvent`. We trust
  this. A real call adds little here.
- **Streaming behavior under strict `json_schema`** (chunk cadence; are partial
  buffers always clean prefixes?): NOT pinned down by the spec. This is the only
  thing a real capture meaningfully validates, and it is exactly the assumption
  phase 6's UI depends on (growing partials must parse).

## What we would do (if revisited)

1. **Committed, key-gated capture tool** - `tool/capture_openai_stream.dart` (or
   a `curl` script). Hits the real endpoint with our *exact*
   `ChatCompletionCreateRequest` (model + `responseFormat: jsonSchema`,
   `tutorResponseJsonSchema`). Gated behind an env var / API key so CI skips it.
   Writes the raw SSE bytes to `test/fixtures/openai_chat_stream.sse`. Capture
   with `curl` (not only the SDK) so the literal bytes are visible independent of
   the SDK; if a future SDK bump mis-parses, raw-vs-decoded diverges visibly.
2. **Offline replay test** - replays the committed raw SSE via `MockClient`
   (exactly like the phase-4 test) and asserts the real assumption:
   - every cumulative buffer parses through `PartialJsonParser` without throwing;
   - the concatenation of deltas reproduces the final bytes exactly (so every
     cumulative buffer is a true prefix);
   - the final buffer parses to a valid `TutorResponse`.
   This runs in CI forever against the fixture; the capture is run occasionally
   by a human with a key.

## Honest scope note

The residual risk is small: the SDK owns parsing and is widely used, and phase 1
is deliberately tolerant - even a non-prefix buffer degrades gracefully rather
than crashing. So this phase is **insurance + living documentation of the
cadence**, not a correctness blocker. The fixture is a non-deterministic sample
(model output varies; OpenAI can change cadence), so it is a known-good example,
not a contract. This is why it is deferred rather than done.

## Done when (if undeferred)

- The capture tool is committed and runs from a documented command with a key.
- `test/fixtures/openai_chat_stream.sse` is committed (raw bytes).
- An offline replay test asserts prefix-validity + final-typed-parse and passes
  in CI without network.

## Trigger to revisit

Any of: partial buffers that fail to parse in the running app; the tutor widget
flickering with malformed intermediate state; an openai_dart major bump; or a
move to the Responses API (`/v1/responses`), whose delta events differ and would
need their own capture.
